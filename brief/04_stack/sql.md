# Стек: sql

> Потребители: исполнители задач с `stack: [sql]` и их ревьюеры.

## Технологии

PostgreSQL 16, чистый SQL (без dbt, Python и процедурной логики вне `DO`-блоков проверок).
Клиент в окружении проверок — `psql` с `ON_ERROR_STOP`.

## model/build.sql

- Собирает всю схему `core` из `raw` одним запуском на чистой базе и **повторно** без ошибок:
  в начале `DROP ... CASCADE` своих объектов (или `DROP SCHEMA core CASCADE; CREATE SCHEMA core;`),
  затем создание и наполнение. Витрины `mart` зависят от `core`, поэтому пересоздаются после.
- `raw` только читается: никаких `ALTER`, `UPDATE`, `DELETE`, индексов на `raw`.
- Типизация на переносе: даты — `timestamp`, деньги — `numeric(12,2)`, количества — `integer`.
  Пустые строки и мусор превращаются в `NULL` явно (`nullif(trim(x), '')`), а не роняют сборку.
- У каждой таблицы: первичный ключ, внешние ключи на соседей, `NOT NULL` там, где данные это
  гарантируют, и комментарий с **зерном** (`COMMENT ON TABLE core.order_items IS 'одна строка —
  позиция заказа'`).
- Ключи: естественные ключи источника, где они устойчивы. Отдельно — покупатель: в `raw`
  `customer_id` новый на каждый заказ, человек — `customer_unique_id` (см. вопрос 4 в
  `docs/tasks.md`). Дубли и несостыковки источника обрабатываются явно и описываются в комментарии.
- Определения, от которых зависят цифры, — в одном месте модели, а не в каждом запросе. Главное:
  какие статусы заказа считаются выручкой и из чего она складывается (цена + доставка позиций или
  оплаты). Оформите это колонкой или представлением в `core` с комментарием «почему так».
- Не теряем строки молча: перед `JOIN` подумайте, всегда ли есть пара; где нет — `LEFT JOIN` и
  явное решение, что делать с «сиротами».
- Индексы — на внешние ключи и даты, по которым режут отчёты; без лишнего.

## model/checks.sql

Самопроверки, которые падают (`RAISE EXCEPTION`) при реальной проблеме модели:
- число строк `core` против `raw` по каждой таблице (с учётом осознанных исключений — их
  количество проверяется явно, а не «примерно»);
- суммы денег до и после переноса;
- нет сирот по внешним ключам там, где ключ не объявлен;
- уникальность объявленного зерна.

## Ответы: mart/answers_*.sql

- Каждый вопрос — представление в `mart`, построенное **только по `core`** (никаких `raw.`):
  `CREATE OR REPLACE VIEW mart.a1_... AS ...`. Файл идемпотентный.
- Перед представлением — комментарий: вопрос, уровень расчёта (заказ / позиция / покупатель) и
  принятые решения.
- Формат блока А фиксирован, его сверяет `checks/control.sql`:

| Витрина | Колонки | Строки |
|---|---|---|
| `mart.a1_monthly_revenue` | `month, orders, revenue` | 24 месяца 2016-09 … 2018-08, пустой месяц тоже есть |
| `mart.a2_top_sellers` | `seller_id, city, state, orders, units, revenue` | 10, по убыванию выручки |
| `mart.a3_avg_check` | `avg_check, avg_lines, avg_units` | 1 |
| `mart.a4_customers` | `customers, returned, returned_pct` | 1; `returned_pct` в процентах (3.12) |
| `mart.a5_category_revenue` | `category, revenue, share_pct` | по категории, без категории — отдельной строкой |

- Следующие вопросы: `mart/answers_b.sql`, витрины `mart.b1_...` и т. д.; формат — как просит
  вопрос.

## Как не писать

- Запросы ответов к `raw` или копии `raw` в `core` без типизации и ключей.
- Модель под конкретный вопрос: таблица `core.monthly_revenue` вместо фактов и измерений.
- Подгонка под контрольную цифру без объяснимой причины. Если цифра не сходится — ищите
  статусы, уровень и потери на соединениях (`docs/tasks.md`, «Что делать, если цифра не сходится»).
- Временные объекты, отладочные `SELECT` и `\echo` в итоговых файлах.

## Стиль

Ключевые слова — заглавными, имена — `snake_case`, таблицы во множественном числе
(`orders`, `order_items`), по одной колонке на строку в `CREATE TABLE`, CTE вместо вложенных
подзапросов глубже двух уровней.

## Команды проверок

`docker compose -f compose.checks.yaml run --rm -T dev sh checks/run.sh` — должна закончиться `OK`.
