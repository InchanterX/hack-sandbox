# Обзор: кейс «Модель маркетплейса Capibara»

> Потребители: все исполнители и ревьюеры; файл попадает в каждый пакет задачи.

## Что делаем

Модель данных маркетплейса в PostgreSQL 16, на которую смогут опереться аналитики. Задание —
[docs/handout.md](../../docs/handout.md), вопросы — [docs/tasks.md](../../docs/tasks.md). Это
не веб-продукт: ничего не разворачиваем, сдаём SQL и тексты.

Оценивают:
- верность ответов: контрольные цифры блока А;
- качество модели и её сопровождаемость;
- умение команды объяснить каждое решение на защите;
- концепцию дашборда и стратегию развития.

Модель, которую никто не может объяснить, оценивается низко, даже если цифры сошлись. Поэтому
простое и явное решение лучше хитрого.

Главный принцип из задания: в середине хакатона придут ещё пять вопросов и вброс. Модель строим
под предметную область (заказы, позиции, оплаты, продавцы, покупатели, товары, отзывы), а не
под пять известных вопросов. Новый вопрос должен решаться запросом к `core`, а не
перестройкой модели.

## Слои

| Схема | Что | Кто пишет |
|---|---|---|
| `raw` | CSV как пришли, все колонки `text` | `scripts/load_raw.py` организаторов. **Не менять** |
| `core` | наша модель: типы, ключи, связи, очищенные данные | `model/build.sql` |
| `mart` | витрины с ответами на вопросы | `mart/answers_*.sql` |

## Где что лежит

```
docs/                   задание и вопросы организаторов (не менять)
scripts/                загрузка данных организаторов (не менять)
docker-compose.yml      база для людей (не менять)
compose.checks.yaml     окружение проверок: db + dev
checks/run.sh           полная проверка с нуля; checks/control.sql — контрольные цифры
model/build.sql         сборка core из raw одним запуском
model/checks.sql        самопроверки модели: ничего не потеряно
mart/answers_a.sql      ответы блока А (витрины mart.a1..a5), дальше answers_b.sql и т. д.
report/                 записка о решениях, концепция дашборда, стратегия
brief/assets/solutions/ решения участников команды в любом виде — исходный материал, не менять
```

## Проверка

Одна команда для всех задач, её же запускает дирижёр:

```sh
docker compose -f compose.checks.yaml run --rm -T dev sh checks/run.sh
```

Она поднимает чистую базу, скачивает и загружает `raw`, дважды собирает модель, выполняет
самопроверки и ответы, печатает витрины и сверяет контрольные цифры блока А. Задача не сдана,
пока команда не завершилась `OK`. После работы: `docker compose -f compose.checks.yaml down -v`.

Доступ к базе во время работы: после запуска проверки сервис `db` продолжает работать, запросы —
`docker compose -f compose.checks.yaml run --rm -T dev psql -c '...'`.
