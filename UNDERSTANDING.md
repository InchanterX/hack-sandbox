# UNDERSTANDING

## Как мы поняли продукт

Проект sandbox-repair — короткий инфраструктурный smoke уже готового HTTP-сервиса. Цель — минимальным изменением проверить полный путь от локальных проверок до публикации контейнера и здорового приложения в Argo. Новый продукт или интерфейс проектировать не нужно.

Итоговый контракт сервиса:

- `GET /healthz` → `200`, `application/json`, `{"status":"ok"}`.
- `GET /` → `200`, `application/json`, `{"message":"sandbox-repair smoke"}`.
- Неизвестный путь → `404`, `application/json`, `{"error":"not_found"}`.

Сохраняем `app/server.py` с `ThreadingHTTPServer`: один процесс Python 3.14, стандартная библиотека (`http.server`, `json`, `unittest`), порт 8080. Один контейнер работает под UID 10001; один ClusterIP Service обеспечивает доступ внутри кластера. Сборка использует существующий `app/Dockerfile` и корень репозитория как context.

Веб-интерфейс, frontend, зависимости pip/npm, БД, внешние API, AI-интеграции и дополнительные сервисы не нужны. Не добавляем endpoints версии и метрик. Системные документы и отчёты прежних smoke сохраняются; credentials не читаем и не коммитим.

## Сценарий демо, пересказанный своими словами

1. После штатного Fusion S2 и планирования S3 выполняем один scaffold S4: сохраняем готовые файлы и проверяем их согласованность. Результат фиксируем в `docs/scaffold-smoke.md`, чтобы scaffold имел содержательный результат. Дополнительные Fusion не нужны; дополнительные задачи выполняются в режиме Solo.
2. В единственной небольшой реализации S5 меняем константу `MESSAGE` в `app/server.py` с `seed` на `sandbox-repair smoke`. Существующие контрактные тесты после scaffold не меняем и функциональность не расширяем.
3. В S6 дополняем `tests/e2e/` проверкой точного итогового сообщения в ответе отдельного процесса сервера и делаем осмысленный коммит. Через сервис `dev` файла `compose.yaml` запускаем `python -m unittest discover -s tests/contract -v` и `python -m unittest discover -s tests/e2e -v`. Проверки работают с checkout без секретов.
4. В S7 Conductor запускает штатную сборку: Build Job публикует один образ `api` в Harbor с SHA-тегом, затем Argo развёртывает `Deployment smoke-api` в `hack-sandbox-repair`. Namespace заранее создаёт оператор. `deploy/images.yaml` должен указывать `app/Dockerfile` и context `.`; сохраняем структуру `deploy/base/` и `deploy/overlays/demo/`. Deployment и Service называются `smoke-api`; readiness и liveness обращаются к `/healthz` через именованный порт `http` (8080).
5. Для показа открываем доступ к сервису через port-forward. Проверяем здоровье, точное сообщение корневого маршрута и JSON-ошибку неизвестного пути. Успех означает, что контрактные и e2e проверки проходят, опубликован один образ `api`, а приложение в Argo находится в состоянии Healthy.

DNS, TLS и HTTPRoute для демо не нужны. Кодовые задания не запускают `kubectl`, `helm` и `argocd`, не меняют SHA-теги вручную и не создают инфраструктурные ресурсы или прикладные секреты.

## Что неясно или противоречиво

Открытых продуктовых вопросов нет: `brief/02_scope.md` прямо фиксирует все решения и требует `questions: []`. Поэтому пакет вопросов пуст; записи в `.orchestra/questions.jsonl` для S1 не создаём.

Известное расхождение с общим шаблоном S3 уже разрешено в `brief/08_deploy.md`: HTTPRoute здесь не нужен, доступ для демо осуществляется через port-forward. Для планирования и проверок используем заданные команды Python через Compose, без npm и новых инструментов.

Оценки времени предварительные; принимаем краткий приёмочный прогон с фиксированным объёмом S4–S7. Это не требует отдельного решения человека. Изоляцию веток считаем исправленной согласно сообщению человека для попытки 4; результаты предыдущего проекта не переносим.

## Риски, которые видны уже сейчас

- Несогласованные имя образа, Dockerfile или build context могут сорвать выпуск при работающем локальном сервере. На S4 нужно сверить `deploy/images.yaml`, Dockerfile и манифесты с требованием одного образа `api`, context `.` и имён `smoke-api`; результат записать в `docs/scaffold-smoke.md`.
- Проверка только типа `message` пропустит оставшееся значение `seed`. S6 должна проверять точную строку `sandbox-repair smoke`, а существующие контрактные тесты после scaffold остаются неизменными.
- Успешный HTTP-ответ локально не подтверждает публикацию образа и состояние Argo. Приёмка релиза отдельно требует успешного Build Job, образа в Harbor и Healthy Deployment с корректными health probes; эти операции выполняет Conductor.
- Общие шаблоны могут привести к лишним зависимостям, публичному маршруту или ресурсам кластера. Здесь не добавляем CI, форматтеры, менеджеры зависимостей, HTTPRoute, Namespace, Secret, RBAC, ServiceAccount, NetworkPolicy, PVC и `deploy/secrets.yaml`; ограничивающие ресурсы уже подготовлены оператором.
- Перенос изменений прежнего проекта нарушит изоляцию и владение файлами. В S1 меняем только `UNDERSTANDING.md` и `questions.yaml`; исключённый из Git `HANDOFF.md` служит для передачи статуса. Прикладной код, brief и защищённые документы в S1 не меняем.
