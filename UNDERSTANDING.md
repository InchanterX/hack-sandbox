## Как мы поняли продукт

Calc Queue — маленький веб-сервис для тестового прогона оркестра. Задача продукта — не сама арифметика,
а показать весь конвейер: backend (Go), frontend (React), devops (compose + Kustomize/Argo), БД, очередь,
авторизацию, секрет в кластере и релиз по URL `https://sandbox.hack.faberge-eggs.ru`.

Что делает продукт:
- Пользователь регистрируется и входит по логину и паролю. Сессия — непрозрачный токен в
  `Authorization: Bearer`, в БД хранится его sha256; выход удаляет строку сессии. Ролей и админки нет.
- Пользователь отправляет арифметическое выражение (`+ - * /`, скобки, унарный минус, целые и десятичные).
  Синтаксис проверяет свой парсер (рекурсивный спуск, `internal/calc`) прямо при создании: ошибка → 422
  `syntax_error`, задача не создаётся.
- Задача попадает в очередь — таблицу `tasks` в Postgres. Пул воркеров в том же процессе (`WORKERS=2`)
  забирает задачи через `FOR UPDATE SKIP LOCKED` и вычисляет их с задержкой `OP_DELAY_MS=700` на каждую
  бинарную операцию, чтобы очередь была видна глазами. Итог — `done` с `result` (float64, 10 знаков,
  `-0` → `0`) или `failed` с `division_by_zero`.
- Фронтенд раз в секунду опрашивает `GET /api/tasks` и показывает живые статусы. Изменить выражение можно
  только у `queued`, удалить — всё, кроме `running`; гонку с воркером снимает условный
  `UPDATE/DELETE ... WHERE status=...` (0 строк → 409).
- Изоляция: пользователь видит только свои задачи; чужой id → 404.
- Надёжность: при старте `running` → `queued`; по SIGTERM воркеры дорабатывают текущую задачу (до 10 с).

Развёртывание: три сервиса (`web` на nginx-unprivileged, `server` на distroless, `db` Postgres 17 как
StatefulSet), один HTTPRoute (`/api` → server, `/` → web). Единственный секрет — `POSTGRES_PASSWORD` в
Secret `db`, его создаёт человек. Проверки всех задач идут в compose-сервисе `dev`.

## Сценарий демо, пересказанный своими словами

1. Открываем сайт без входа — нас отправляют на `/login`, там есть ссылка на регистрацию.
2. Регистрируем `alice` / `alice-pass-1` — сразу оказываемся на `/` с пустым списком и подсказкой
   «Задач пока нет — отправьте первое выражение».
3. Отправляем `2 + 3 * (4 - 1)` — строка появляется со статусом «в очереди».
4. Сразу же отправляем `(10 - 4) / 3` и `7 / (2 - 2)`. Воркеров два, задач три, поэтому одна задача заметно
   ждёт в «в очереди», пока две «выполняются». Первая задача — 3 операции ≈ 2,1 с, вторая — 2 ≈ 1,4 с.
5. Без перезагрузки (опрос раз в секунду) видим `11`, `2`, а у третьей — «ошибка» с текстом
   «деление на ноль». Сервер продолжает работать.
6. Отправляем `100 / 7 + 1`, пока она в очереди, жмём «Изменить», меняем на `100 - 7` и сохраняем —
   воркер считает уже новое выражение, итог `93`. (Чтобы окно «в очереди» точно было, перед этим шагом
   ведущий занимает обоих воркеров двумя длинными выражениями — см. Q1.)
7. Вводим `2 + * 3` — форма сразу показывает «синтаксическая ошибка» под полем (ответ API 422), строка не
   появляется.
8. Удаляем задачу со статусом «ошибка» — она пропадает из списка.
9. Выходим, регистрируем `bob` — у него пусто. Выходим, входим под `alice` — все её задачи на месте.

Этот же сценарий по API повторяет e2e в `tests/e2e/` (`node --test`, сервер с `OP_DELAY_MS=50` против `db` из
compose), плюс проверки критериев: 401 без токена, 409 `login_taken`, 409 `not_queued`, 409 `task_running`,
404 на чужую задачу, `running` → `queued` после перезапуска.

## Что неясно или противоречиво

<!-- Каждый пункт ведёт к вопросу в пакете S1 (Q1, Q2, ...). -->

- **Q1. Шаг 6 не воспроизводится как написан.** После шага 5 оба воркера свободны, `POLL_INTERVAL_MS=300`,
  поэтому `100 / 7 + 1` уйдёт в `running` через ≤0,3 с — нажать «Изменить» не успеть. В e2e с
  `OP_DELAY_MS=50` окна тем более нет. Нужен способ гарантировать окно `queued`.
- **Q2. Язык `error.message`.** В контракте пример английский (`unexpected '*' at position 4`), а фронтенд
  обязан показывать `error.message`, и демо ожидает русские тексты («синтаксическая ошибка», «логин занят»,
  «деление на ноль»). Для `division_by_zero` русский текст задан явно, для остальных — нет.
- **Q3. Место в очереди после PATCH.** Очередь сортируется по `created_at`; не сказано, переставляет ли
  изменение задачу в конец.
- **Q4. Код ошибки для запрещённых символов.** `expression` допускает только цифры, `.`, `+ - * /`, скобки,
  пробелы; для `2 ^ 3` или `2 + x` подходят и `syntax_error`, и `validation_error`.
- **Q5. Длина пароля 8–72 — символы или байты.** bcrypt обрезает/отклоняет больше 72 байт, а кириллица
  занимает 2 байта на символ.
- **Q6. Формат десятичных чисел.** Допустимы ли `.5`, `5.`, `007`.

Мелочи, которые решаем сами (без вопроса людям):
- Выражение без операций (`5`, `(5)`) — валидно, результат сразу, задержки 0.
- Повторный унарный минус (`--5`, `2 * -3`) разрешён: унарный минус имеет высший приоритет, грамматика это
  допускает.
- Невалидный uuid в `/api/tasks/{id}` → 404 `not_found` (как несуществующий).
- Логин хранится и сравнивается как есть; форма не меняет регистр, ввод `Alice` → 422 `validation_error`.
- Список задач без пагинации (нагрузка — единицы пользователей).
- Отображение результата: число из API как есть (`14.2857142857`), без локализованной запятой.
- `tasks.yaml` (`npm run lint/test` на корне) и `deploy/images.yaml` (`app`, context `.`) пока шаблонные и
  расходятся с brief (Go + `server/`, `web/`); их приводит в соответствие S3/S4 по brief, вопрос людям не нужен.

## Риски, которые видны уже сейчас

- **Тайминги демо.** Видимость очереди (шаг 4) и окно для «Изменить» (шаг 6) зависят от `WORKERS`,
  `OP_DELAY_MS`, `POLL_INTERVAL_MS` и скорости ведущего; без явного приёма (Q1) демо может сорваться вживую.
- **Гонка изменения и забора.** PATCH и воркер должны конкурировать только через условный `UPDATE ... WHERE
  status='queued'`; воркер обязан вычислять выражение, прочитанное в том же `UPDATE ... RETURNING`, иначе
  шаг 6 даст `15.2857142857` вместо `93`.
- **Перезапуск посреди вычисления.** Возврат `running` → `queued` при старте безопасен только при одной
  реплике сервера; при rolling update двух подов старый под ещё считает, а новый уже сбросит его задачу.
  Нужна стратегия `Recreate` (или maxSurge 0) в Deployment `server`.
- **Плавающая точка.** `float64` + округление до 10 знаков: `(10 - 4) / 3` должно дать ровно `2`, `-0` → `0`;
  нужны табличные тесты на граничные значения и сериализацию JSON (без `2.0000000000000004`).
- **Ограничения кластера.** AppProject `hackathon` запрещает ServiceAccount/Role/NetworkPolicy и
  cluster-scoped объекты; Secret `db` создаёт человек — без него `db` и `server` не стартуют. Квота: до 4 PVC,
  нам нужен 1.
- **Миграции при старте и startupProbe.** Сервер применяет goose до готовности; startupProbe до 60 с, а
  Postgres в StatefulSet может подниматься дольше при первом создании PVC — сервер должен ретраить
  подключение, а не падать в CrashLoop.
- **Герметичность тестов.** Воркеры с задержкой нужно тестировать без `sleep` (`testing/synctest` или
  инъекция часов/задержки), иначе нарушим TEST-11 и `-race`/`goleak` начнут флакать.
- **Общие файлы scaffold.** Роуты, миграции, `go.mod`, `package.json` правит только scaffold; задачи,
  которым нужна правка, ждут дирижёра — риск блокировок на S5, если S4 что-то упустит.
