# UNDERSTANDING

## Как мы поняли продукт

`sandbox-release` — инфраструктурный smoke-прогон уже существующего приложения, а не новый продукт. Нужно подтвердить, что минимальное изменение проходит проверки, сборку, публикацию и развёртывание. Единственное изменение поведения — заменить `MESSAGE = "seed"` в `app/server.py` на `"sandbox-release smoke"`.

Сохраняем один процесс `ThreadingHTTPServer` на Python 3.14 со стандартной библиотекой, один контейнер под UID 10001 и один ClusterIP Service. Порт приложения — 8080. Все ответы — `application/json`:

| Запрос | HTTP-статус | Итоговое тело |
| --- | --- | --- |
| `GET /healthz` | 200 | `{"status":"ok"}` |
| `GET /` | 200 | `{"message":"sandbox-release smoke"}` |
| `GET /not-a-route` и другие неизвестные пути | 404 | `{"error":"not_found"}` |

Не нужны frontend, framework, pip/npm-зависимости, БД, внешние API, AI-интеграции, новые сервисы, endpoint версии или метрики. Приложение не обращается к API Kubernetes и не требует прикладных секретов.

Объём работ уже задан; результат каждой следующей стадии можно проверить по конкретному артефакту:

| Стадия | Ожидаемый результат |
| --- | --- |
| S3 — план | В `tasks.yaml` заданы Compose `dev`, контрактная и e2e команды из brief; предусмотрены один scaffold S4, одна реализация S5 и штатные S6/S7. |
| S4 — scaffold | Готовые файлы сохранены и согласованы; содержательный `docs/scaffold-smoke.md` перечисляет проверенные файлы. |
| S5 — реализация | В `app/server.py` значение `MESSAGE` заменено с `seed` на `sandbox-release smoke`. |
| S6 — e2e | В `tests/e2e/` есть проверка точного итогового сообщения от отдельного процесса и осмысленный коммит. |
| S7 — релиз | Штатный конвейер публикует один образ `api`, Argo развёртывает приложение до Healthy. |

Контрактные тесты после scaffold не меняем. Штатный Fusion стадии S2 сохраняется, дополнительных Fusion нет; дополнительные задачи выполняются в режиме Solo. Системные документы и отчёты прежних smoke сохраняем. CI, форматтеры и менеджеры зависимостей не добавляем.

## Сценарий демо, пересказанный своими словами

1. В существующем окружении Compose (`compose.yaml`, сервис `dev`, checkout доступен без секретов) запускаем контрактные проверки `python -m unittest discover -s tests/contract -v` и e2e `python -m unittest discover -s tests/e2e -v`. После S6 e2e должен проверять запуск отдельного процесса и точное итоговое сообщение.
2. Conductor штатным Build Job собирает единственный образ `api` из `app/Dockerfile` с контекстом в корне репозитория и публикует его в Harbor с SHA-тегом. Conductor также выполняет синхронизацию Argo; вручную SHA-теги не меняем.
3. Argo развёртывает Deployment `smoke-api` и Service `smoke-api` в namespace `hack-sandbox-release`, заранее созданном оператором. Readiness и liveness проверяют `/healthz` на именованном порту `http` (8080). Приложение должно стать Healthy.
4. Через port-forward к `smoke-api` клиент проверяет три ответа из таблицы: здоровье, точное сообщение smoke и JSON-ошибку неизвестного пути. DNS, TLS и HTTPRoute для этого демо не нужны.

Успех — одновременно зелёные контрактные и e2e проверки, публикация одного образа `api` и Healthy-развёртывание с правильными HTTP-ответами. Один успешный локальный запрос ещё не подтверждает весь релизный конвейер. Это ожидаемый сценарий приёмки после S5/S6, а не отчёт об уже выполненном релизе: в S1 изучены brief и исходные файлы, проверки приложения, сборка и развёртывание не выполнялись.

## Что неясно или противоречиво

Открытых вопросов к людям нет: `brief/02_scope.md` прямо фиксирует все продуктовые решения и требует `questions: []`. Поэтому пакет `questions.yaml` пуст, разумных дополнительных решений для человека не требуется. HTTPRoute из общего шаблона S3 здесь не применяется — это явно оговорено в `brief/08_deploy.md`.

В исходных файлах есть несоответствия готового шаблона требованиям: `tasks.yaml` пока содержит npm-команды и примерные задачи; `deploy/images.yaml` объявляет образ `app` без явного пути к Dockerfile, хотя brief и Deployment требуют `api` и `app/Dockerfile`. Это не неоднозначность продукта: в S3 нужно привести план к brief, а в S4 согласовать декларацию образа с существующим Dockerfile и deploy-манифестами. В S1 эти файлы не меняем. Значение `seed` в приложении и SHA-заглушка `newTag: seed` в overlay ожидаемы до следующих стадий: сообщение меняет S5, а тег образа — штатный Conductor при релизе.

## Риски, которые видны уже сейчас

- **Неверный план проверок.** Текущие npm-команды в `tasks.yaml` не соответствуют стеку без npm. В S3 нужно задать `check_env` через Compose `dev`, контрактную команду и отдельную e2e-команду из brief; оставить ровно предусмотренный объём задач.
- **Несогласованная сборка образа.** Имена `app` в декларации образов и `api` в Deployment расходятся; путь к существующему Dockerfile не указан в декларации. S4 должен проверить согласованность декларации, Dockerfile, Compose и deploy-манифестов, иначе сборка или подстановка образа может не дать требуемый релиз.
- **Ложноположительная e2e-проверка.** Сейчас тест корневого ответа проверяет только тип строки и пропустит `seed`. S6 должен проверять точное `sandbox-release smoke`; контрактные тесты после scaffold сохраняются неизменными.
- **Зависимость от инфраструктуры.** Прохождение локальных тестов не доказывает доступность Harbor, успешность Build Job, готовность namespace или синхронизацию Argo. Это проверяется на штатном релизе; сборку, публикацию и синхронизацию выполняет Conductor, namespace и ограничивающие ресурсы готовит оператор.
- **Лишнее расширение smoke.** Общие шаблоны могут подтолкнуть к добавлению CI, публичного маршрута или инфраструктурных ресурсов. Здесь запрещено добавлять Namespace, Secret, RBAC, ServiceAccount, NetworkPolicy и PVC в Application; `deploy/secrets.yaml` не нужен. Из кодовых заданий не запускаем `kubectl`, `helm` или `argocd`; port-forward остаётся способом просмотра демо.
